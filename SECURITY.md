# Security

## Reporting a vulnerability

Please use GitHub's private vulnerability reporting ("Report a vulnerability" on the Security tab) rather than a public issue. That keeps the report private until a fix exists.

⚠ **Set your expectations by the project status in the README**, which promises no support. A report may not get a timely answer, or any answer. That is a poor position for a security channel to be in, so it is said plainly rather than left to be discovered: if you find something serious here, assume you may need to act on it yourself — the licence permits a fork, and much of this code is shared with [xai-org/grok-build-plugin-cc](https://github.com/xai-org/grok-build-plugin-cc), where a defect inherited from upstream is worth reporting regardless of what happens to this fork.

This is a personal fork maintained alongside other work, so please do not expect a same-day response.

## What this plugin does with your data

**It runs an external CLI.** Every task is handed to the real `grok` binary, which sends it to the Grok service. Prompts, file contents the agent reads, and its output leave your machine. Nothing in this plugin changes that, and no local setting prevents it.

**Prompts and results are written to disk.** Job records, logs, and state live under the plugin data directory. Prompts too long for the command line are written to a temporary file that is deleted after the run. Job logs, state files and those temporary prompt files are created `0600`. On Windows that mode is largely advisory — treat the state directory as readable by anything running as your user.

**Secret-shaped strings are redacted** in job logs and in the progress text stored on job records: `sk-…`, `xai-…`, `Bearer …`, and `KEY=`/`TOKEN=`/`SECRET=` assignments. This is a safety net for accidental leakage into diagnostics, not a guarantee. Do not put credentials in prompts.

**The request and the model's result are stored verbatim, and that is deliberate.** Redaction covers the diagnostic surfaces named above; the run's actual output — `result` and the rendered text on the job record — is written exactly as it came back. It has to be: it is the deliverable you read, and a review of code that discusses key formats would be mangled by a filter that cannot tell a quoted example from a live credential. The request is kept the same way: a background run persists the whole request on its job record, prompt included, and the opening of that prompt becomes the run's summary in the workspace state index. The consequence is worth stating plainly rather than leaving to be discovered: anything the model echoes back, including a secret it was shown, lands on disk unredacted under the plugin data directory — and so does a secret pasted into the prompt, which is the likelier place for one to appear.

**The `grok` CLI child inherits a filtered environment**, not your full one. What passes: a small fixed list of OS variables the process needs to start (`PATH`, `PATHEXT`, `SystemRoot`, the temp directories, locale), plus anything beginning `GROK_` or `XAI_` — the credentials the CLI itself needs. Nothing else reaches it — in particular not other vendors' API keys, which a process talking to Grok has no use for. This allowlist is the fork's own; upstream has none, so do not assume this behaviour of the original plugin.

The filter covers the process that talks to somebody else's service, and only that one. The OS helpers the bridge runs to look at processes (`tasklist`, `ps`, `taskkill`) and its own detached run-worker are handed the full environment: they are local utilities and this program re-executing itself, not third parties.

`NODE_OPTIONS` and `NODE_PATH` are also deliberately **not** forwarded. They are the two best-known ways to make a Node process load code nobody asked for — `--require` runs a file before anything else, and `NODE_PATH` redirects bare module resolution — and the CLI does not need either. The parent environment belongs to the user, so this is not a remote attack path; it is one step fewer for anyone who already has that environment, which is what a filter is for.

## The CLI can send more than the task, and that is its setting to change, not this plugin's

Everything above is about what the *bridge* does. The `grok` CLI has a second channel of its own, separate from inference, and it is worth knowing about because nothing here touches it: telemetry and a per-turn trace-upload pipeline. This plugin sends no telemetry and uploads no content of its own — it runs the CLI you already have, under your own account — so what follows is a property of that CLI, and the knobs belong to it.

⚠ **One exception, and it is the only outbound request this plugin makes by itself: the update check.**

- **What is sent:** one unauthenticated `GET` to the public GitHub endpoint `repos/kai-wedekind/claude-code-grok-bridge/releases/latest`. No body, no token, no identifier, no telemetry. GitHub necessarily sees your IP and a `grok-build/<version>` user-agent, which is the version you are running.
- **When:** at **SessionEnd** only — at most once every six hours after a successful check, and after a failure on a backoff that starts at one hour and doubles to a ceiling of one day. Never if the session's own cleanup already used most of its budget. Never at SessionStart — that hook has a five second budget and it is the one whose 0.3.2 defect this whole feature exists to warn people about. SessionStart only reads a small cached file.
- **What it does with the answer:** writes `<state root>/update-check.json` and, on the next session start, may print one line telling you a newer version exists. **It never downloads or installs anything.**
- **Turning it off:** `GROK_CC_UPDATE_CHECK=0` (also `off`, `false`, `no`). It is read from the hook's own environment, so it is not the inert kind of switch described under [The CLI can send more than the task](#the-cli-can-send-more-than-the-task-and-that-is-its-setting-to-change-not-this-plugins) — set it however you set variables for Claude Code and no request is made.
- **If the check fails or has never run, the plugin says nothing.** It will not tell you that you are up to date, because it does not know.

Verified against the CLI installed here, which carries its own documentation inside the binary:

| What | How to turn it off |
|---|---|
| Coding data sharing | `grok`, then `/privacy` |
| Telemetry | `GROK_TELEMETRY_ENABLED=0`, or `[features] telemetry` in `config.toml` |
| Per-turn trace upload | `GROK_TELEMETRY_TRACE_UPLOAD=0`, or `[telemetry] trace_upload` |
| Product analytics (Mixpanel) | `GROK_TELEMETRY_MIXPANEL_ENABLED=0` |
| Feedback collection | `GROK_FEEDBACK_ENABLED=0` |

Every name above appears in the CLI's own environment-variable reference, which is embedded in the binary. That matters because of what is *not* in the table, below.

Three honest limits. First, these are the CLI's own knobs and the CLI is xAI's software: what each one covers, whether any of it is additionally gated server-side, and how long anything is retained are theirs to define and change — check their current terms rather than trusting a list written here. Second, the bridge forwards `GROK_*` and `XAI_*` to the child (see above), so setting these in the environment does reach the CLI when the bridge launches it — but a setting you make only in your shell will not follow a run started from somewhere else. Put them where they will be there every time.

Third: **there is a widely-repeated `DISABLE_ERROR_REPORTING=1` switch, and setting it for a bridge-launched run does nothing.** The name matches neither the `GROK_`/`XAI_` prefixes nor the exact allowlist, so the env filter strips it before the CLI is spawned — a control that looks applied and is not, which is worse than a gap. It is also absent from the CLI's own documented variable list; the string exists in the binary next to a `GROK_ERROR_REPORTING` spelling that *would* survive the filter, but neither is documented and we have not verified what either one does, so we are not going to tell you to set them. If you want that channel off, take it up with the CLI directly rather than through this bridge.

Credit where it is due: this exposure was pointed out to us by [tylersue/claude-grok-delegation](https://github.com/tylersue/claude-grok-delegation), which documents it in its own security notes. We verified the knobs against the installed CLI before writing them down here rather than repeating them on trust — and you should treat this table the same way.

## Your Claude Code Hooks Run Inside Bridge Runs

The Grok CLI reads hooks from Claude Code's own settings, `~/.claude/settings.json` and `settings.local.json`, as global hook sources with no trust prompt, and the switch for that is on by default (cli-1.0.45 `crates/codegen/xai-grok-hooks/src/discovery.rs:341-383`; the switch is `GROK_CLAUDE_HOOKS_ENABLED`, `crates/codegen/xai-grok-config/src/compat.rs:168`, on by default at `:297-305`). Measured 2026-10-15 on grok 1.0.52: `grok inspect` listed every hook from the Claude Code settings on that machine. So every bridge run executes your Claude Code hooks, read-only reviews of somebody else's repository and connector runs included. A hook is your program, not a tool the agent calls, so the layers this fork relies on, tool removal and deny rules, do not apply to it; whether a kernel sandbox, where one is enforced, also confines hook processes has not been measured. What a hook is handed, the run's tool calls, is shaped by the same untrusted content as the run itself. A project's own hooks (its `.claude/settings.json`, `settings.local.json` and `.grok/hooks`) load only when the CLI treats that folder as trusted. A headless session such as a bridge run counts as untrusted unless the folder was recorded as trusted, so with the CLI's defaults a repository you merely review does not get its hooks run. That is the CLI's gate, not the bridge's, and it opens in two cases: folder trust switched off, through `GROK_FOLDER_TRUST`, the CLI's config or managed config, or a remote setting, and a folder that is your home directory or the filesystem root, which the CLI cannot record and therefore trusts, so do not point `--cwd` at either. All of this is read from the 1.0.45 source, not measured.

The bridge leaves this on, deliberately. The hooks are code you installed, and some of them are guards you want to hold in a Grok session as much as in Claude Code; a bridge that quietly switched them off would remove protection you put there on purpose. To turn them off for bridge runs, set `GROK_CLAUDE_HOOKS_ENABLED=false`. `GROK_` variables reach the child, so the CLI sees it.

Two consequences. A hook that blocks a connector call is expected to show up in the session history the way a refused call does, and the bridge cannot tell the two apart; that is read from the shape of the history, not measured. And recent CLIs load this plugin as a Grok plugin too, so its own session hooks would also run inside the sessions the bridge starts. They recognise the `GROK_CC_BRIDGE_CHILD=1` mark the bridge sets on every Grok session it starts and exit without doing anything.

## Grok's Memory Is Off in Bridge Runs

Since 0.4.0 the bridge sets `GROK_MEMORY=0` for every Grok session it starts unless you set `GROK_MEMORY` yourself: `run`, `review`, `critique`, connector runs and the `check --verify-tools` session. A bridge run is meant to be a self-contained job. What it should know arrives in the prompt, and continuity between runs goes through `--thread`, explicitly. With memory on, a run can store what it saw, a connector run's calendar results for instance, and the CLI can inject it into later, unrelated runs. The stores are kept per workspace, and both memory implementations also have a global one (cli-1.0.45 `crates/codegen/xai-grok-memory/src/lib.rs:10-19` for the original, `v2.rs:3-5` for v2, whose global manifest is injected next to the workspace one at `crates/codegen/xai-grok-shell/src/session/helpers/memory_context.rs:85-108`), so "unrelated" is not limited to the same repository. The model calls behind memory (capture and Dream consolidation) also never appear in the run's usage envelope, so they would be spend this plugin's ledger cannot see.

Memory is off by default in the CLI, but remote settings can switch it on without you doing anything, and that has been observed: the CLI's remote-settings cache (`~/.grok/settings_cache.json`) carried `memory_enabled: true` and `memory_v2.enabled: true`, and bridge runs started with memory v2 enabled (the `memory_v2_enabled` field of a session's `prompt_context.json` shows it). `GROK_MEMORY=0` turns off both memory implementations for the whole process, and the `/memory` toggle cannot turn it back on (cli-1.0.45 `crates/codegen/xai-grok-config-types/src/memory.rs:577-578`, `:675-700`).

A `GROK_MEMORY` you set yourself, to any value, is passed through unchanged, so `GROK_MEMORY=1` is how to keep memory in bridge runs. ⚠ That includes a value the CLI cannot read as a switch: it accepts `1`, `true`, `yes`, `on`, `enabled` and their opposites, and anything else, an empty value included, counts as not set, which leaves memory to your config and to remote settings (cli-1.0.45 `crates/codegen/xai-grok-env/src/registry.rs:13-23`). The bridge does not second-guess it: a variable you exported is treated as your decision.

## Stopping a run checks what it is about to signal

`stop` and `SessionEnd` terminate processes by pid, and those pids come off a job record that may be days old. Operating systems reissue pids, so the number alone is not an identity. ⚠ **Reclaim signals nothing.** An abandoned-but-alive run is delisted, its spend marked incomplete rather than zero, and its kill targets kept on the record so an explicit `stop` can still end it; nothing is killed automatically, precisely because fifteen minutes is ample time for a pid to have been reissued to another agent carrying the same image.

Every record therefore stores the image name of what it started — `bridgeImage` for the bridge process, `agentImage` for the Grok agent — and every kill probes the target and compares before signalling. A mismatch is reported as `image-mismatch` and nothing is terminated.

A record that carries a pid and no name gets a weaker check rather than none: the target must at least be one of the two things a run can start — this interpreter, or the configured `grok` binary (`GROK_BINARY` is honoured). Anything else is refused.

A probe that cannot read the image at all still allows the kill. That is about platforms where the process table is unreadable, not about records that never said.

## Repository content is not trusted input

`review`, `critique` and `run` put repository content into the prompt: the diff, and the contents of untracked files up to 24 KiB each. That content is written by whoever wrote the repository, and a language model does not reliably distinguish "text I was asked to review" from "instruction addressed to me".

The practical rule follows from that, and it is the one thing worth knowing before pointing this at code you did not write:

- **Do not pass `--write` on a repository you do not trust.** In write mode the agent has `Bash`, `Write` and `Edit` in that working directory. A file in the repository that tells it what to do is an input it may act on.
- Read-only mode is a real defence **against the agent writing**: the writing tools are removed rather than merely discouraged. Its scope is the agent, though, and the agent is not the whole run. Gathering the review context runs `git` inside the target directory *before* the agent is launched, so whatever git is willing to take from a directory it is pointed at is taken while the barrier is not yet in play.

  ⚠ **Several git settings take a command as their value, and git honours the ones a repository carries in its own configuration — and a repository can also simply ship a hook. That is git's design, not a git defect** — a local config is trusted, and there is no "untrusted repository" mode to turn on. Since 0.3.3 every git invocation used for context collection disables hooks outright and neutralises the command-valued settings we identified and measured, enumerating the ones with attacker-chosen names per repository rather than assuming a fixed set.

  🚫 **Read that as defence in depth, and specifically not as a claim that the class is closed. It is not, and we have stopped pretending it can be closed this way.** Repeated adversarial testing kept finding a mechanism not named before — a converter, a filesystem monitor, a filter, a config include, a hook, a hook directory whose name was the defence itself, a child process spawned to check whether a submodule was dirty. Each was demonstrated with a live control and each was closed. **The pattern did not converge**, and the reason is structural rather than a matter of effort: git treats a repository's own configuration as trusted, offers no untrusted-repository mode, and adds mechanisms over time. Neutralising them one at a time cannot keep a promise that git does not make.

  So the honest statement is: **known mechanisms are closed and gated, unknown ones are assumed to exist.** Two residuals are known and deliberately *not* closed, because neither can be: a filter named by a committed `.gitattributes` but defined in *your own* global configuration runs your program — a clone carries attributes, so cloning does not help — and configuration reachable through scopes we do not enumerate may name another. The hook path is worth singling out, because it needed no configuration entry at all: a script in the default `.git/hooks` directory was enough, which is why sweeping config keys never found it.

  **Cloning helps and does not finish the job.** A `git clone` does not bring the remote's local configuration, so it removes the case where the repository carries its own command strings — and a directory obtained as an archive, a copied working tree, a shared folder or an rsync does carry them, which is the case worth avoiding. If you have been handed a directory rather than a URL, clone from it before reviewing.

  ⚠ **But a clone does carry `.gitattributes`, and that is enough on its own.** A committed `*.bin filter=lfs` runs the reviewer's *own* `git-lfs` during collection, because the filter is resolved from whatever configuration the reviewing machine already has. The command is then yours rather than the attacker's — but the reviewed tree still decided that a program would run, and which one. Anyone who reviews untrusted code on a machine with globally configured filters should know that; this is the residual we have not closed, and "clone it first" does not reach it.
- **It is not a defence of confidentiality, and the difference matters here.** No *reading* tool is removed — that is what the mode is for. `--cwd` sets the agent's working directory and the base for relative paths. It does not bound what a run can read. In cli-1.0.45, `read_file`, `list_dir` and `grep` accept absolute and `~`-prefixed paths, the CLI does not ask before such a read, and the read-only sandbox profile does not restrict reads. The same design is in 1.0.41. 1.0.52 is unverified from source. So a read-only, review, critique or connector run can read any file the user account can read, including `~/.ssh`, `~/.claude` and `~/.grok`. Instructions planted in a repository, or a connector payload, can ask the agent to pull such files into its context and to restate them in the reply, and from a connector run into a writable connector. Reviewing a hostile repository read-only protects what you keep on disk from the agent's writes; it does not protect what you show. Read the result before you trust it.
- Files ignored by git are excluded (`--exclude-standard`), so the usual `.env` does not travel. Symlinks are detected with `lstat` and named without being opened — reading them would follow the link out of the repository, which is exactly the defect this fork inherited and fixed (upstream `xai-org/grok-build-plugin-cc` issue #4, opened 2026-07-16 and still open there when last checked 2026-08-01).

There is no sanitisation of repository content, and none is claimed. Treat the read-only barrier as the boundary.

## Fetched content is not trusted input either

The section above is about the repository, because that is the case this fork was built around. It is not the only content that reaches the model, and the same non-claim covers the rest of it.

Read-only removes fourteen tools — the shell, the file editor, the two MCP meta-tools, `write`, `monitor`, the four media generators (each of which puts a file on disk), `web_fetch`, and all three scheduler tools, whose entries would outlive the run — and denies `Bash`, `Write`, `Edit` and `MCPTool`. Several of those *can* reach the network, and removing them closes those paths along with the write paths. What it does not close is the one deliberately left open. **So read-only is a write barrier that shuts most outbound doors as a side effect — not a network barrier that shuts them all**, and the door left open is the whole of your exposure here.

`web_search` is deliberately kept, and that is a decision rather than an oversight: this fork carries research offloads as well as code review, and looking things up is frequently the task. The reasoning sits beside the list where it is defined, and a test pins it so it cannot be dropped by accident.

So, on the same terms as the repository:

- **What the agent fetches is untrusted input.** A search result can carry text addressed to the model as easily as a README can. Nothing delimits it, tags it, or marks it as untrusted — and this bridge could not do so if it wanted to, because it never sees it. Tool results live inside the CLI process; the bridge composes a prompt and reads back a final answer.
- **`--cwd` does not reach this.** It sets the working directory. It does not bound what can be read from disk — the previous section is the filesystem claim, and a narrow `--cwd` does not limit it — and it places no constraint on the network path either. Do not read it as covering either one.
- **The sandbox does not close it either, on any platform.** The Grok CLI documents that web search, web fetch and the LLM API always have network access, because the agent needs the network to function.

If you want a run that cannot search, the CLI has `--disable-web-search`. This bridge does not pass it today.

Verified for `run`. `review` and `critique` additionally pass `--agent explore`, whose effective toolset is not something we have pinned down; it may be narrower. Treat the above as the conservative case rather than assuming the narrower one.

## The read-only barrier

`run` is read-only unless `--write` is passed. The barrier is enforced by removing the writing tools from the agent (`--disallowed-tools`) and adding deny rules for `Bash`, `Write`, `Edit` and `MCPTool`.

`--sandbox read-only` is passed on Windows, on macOS, and on Linux when Landlock is present or the probe cannot tell. On a Linux kernel whose active LSMs do not include Landlock the bridge passes `--sandbox off` instead — explicitly, so a sandbox profile in the user's own Grok config or `GROK_SANDBOX` cannot select `read-only` again. A managed requirement still outranks the CLI flag and can force a profile. The confinement record says the sandbox was not requested. **It is not the barrier this fork relies on** either way: xAI documents enforcement through Landlock (Linux) and Seatbelt (macOS) and names no Windows mechanism. **Measured 2026-08-08 against `grok 1.0.0 (3cd0d0cbce)`:** a direct `grok -p "<create a file>" --sandbox read-only --cwd <empty dir>`, with no plugin involved, exited `0` and the file was there afterwards. On Windows the flag is accepted and the write still lands. That was still true of grok 1.0.70 on 2026-10-24 (acceptance step 2b: write landed, exit 0). We do not rely on it anywhere.

⚠ **And the CLI does not say so.** In that run stderr was empty — no warning, no note, nothing that distinguishes an enforced sandbox from an ignored one. The line reading `Sandbox not enforced on this platform (win32)` is emitted by **this bridge** (`describeConfinement` in `grok-bridge.mjs`), not by the CLI.

⚠ **And "Linux" is not the right unit.** Landlock is a kernel configuration option, not a property of the platform. **Measured 2026-08-09 on Raspberry Pi OS (`6.12.96+rpt-rpi-2712`, aarch64):** `/boot/config-$(uname -r)` carries `# CONFIG_SECURITY_LANDLOCK is not set`, and `/sys/kernel/security/lsm` lists only `capability`. On that kernel an older CLI behaved exactly as it does on Windows — flag accepted, exit `0`, stderr empty. **Measured again 2026-10-24 on the same kernel, grok 1.0.70:** `grok -p "say ok" --sandbox read-only --output-format json` exits 1 before any model call, stdout empty, stderr `error: could not apply the 'read-only' sandbox profile; see the warning above for the cause. Refusing to start with its protections missing.` The public 1.0.45 source already does this: every profile except `devbox`, `off` and a custom profile that extends `devbox` requires hook write-deny (`crates/codegen/xai-grok-sandbox/src/hook_write_deny.rs:21-23`, `src/lib.rs:54-66`; the custom-profile exemption is `src/lib.rs:60-62`, but the refusal condition at `crates/codegen/xai-grok-shell/src/config/mod.rs:1475-1480` is `is_custom || needs_hooks`, so every custom profile still counts for the refusal), and `crates/codegen/xai-grok-shell/src/config/mod.rs:1473-1496` exits 1 with that message when such a profile could not be applied. `--sandbox off` (`ProfileName::Off`, `profiles.rs:70-76`, displayed as `off` at `profiles.rs:93`) skips that branch. The bridge therefore passes `--sandbox off` on Linux when its own probe says Landlock is absent, so a sandbox profile in the user's Grok config or `GROK_SANDBOX` cannot re-trigger the refusal — a managed requirement still outranks the CLI flag (cli-1.0.45 `crates/codegen/xai-grok-shell/src/agent/config.rs:632-643`, precedence requirement > CLI > env > config) and can force a profile — and reports `kernelSandbox: "not-requested"`. An unanswered probe is not treated as a no: the bridge still passes `read-only`, and if the CLI then refuses, the run fails with the CLI's own message. Tool removal and deny rules are the whole barrier on that kernel. The 2026-08-09 "flag accepted, exit 0, stderr empty" result describes the older CLI, not this one.

⚠ **The likely way to land in that unanswered case is a container.** Where `/sys/kernel/security/lsm` cannot be read, as in a container that does not mount securityfs (expected, not measured here), the probe answers unknown (`detectLandlock` in `grok-bridge.mjs`), the bridge passes `read-only`, and on a host kernel without Landlock the CLI refuses to start: every read-only `run`, `review`, `critique` and connector run fails with the CLI's refusal on stderr. That is deliberate. Falling back to `off` whenever the answer is unknown would turn "unknown" into "unconfined" without anyone being told, on exactly the runs that read code you did not write. If you know the kernel has no Landlock, `GROK_CC_LANDLOCK_PROBE=absent` (next paragraph) makes the bridge pass `--sandbox off`, and the confinement record says the answer was forced.

`GROK_CC_LANDLOCK_PROBE` (`present`, `absent`, `unknown`) and `GROK_CC_CONFINEMENT_PLATFORM` (`linux`, `win32`, `darwin`, and only while that probe override is set) are test seams that switch the kernel answer without probing the host, so setting `GROK_CC_LANDLOCK_PROBE=absent` on a Landlock host drops the kernel layer: the bridge passes `--sandbox off`, and the confinement record says the answer was forced rather than claiming the host was measured.

⚠ **On that kernel the write landed, and the CLI still said nothing** — the same outcome as Windows, for the same reason, and that sentence describes the 2026-08-09 CLI: asked for a control it had no way to apply, it applied nothing and reported nothing. `scripts/acceptance.sh` step 2b resolves the mechanism in three states — present, absent, unknown. On an unknown POSIX host, step 2b skips rather than judging only when the CLI ran; a CLI that exits non-zero with empty stdout is graded FAIL ("did not run"). Absent now expects the refusal measured on 2026-10-24 (exit non-zero, empty stdout, the refusal sentence on stderr, no file written) and reports that as the documented fail-closed behaviour, not as a skip and not as a held sandbox. Current CLIs refuse to start; they do not silently run.
Note the narrower claim — "not enforced" rather than "does nothing": xAI documents effects that follow from merely *requesting* a profile, so calling the flag inert would still be an overstatement, and in a security document an overstatement in the comfortable direction is the wrong one to make. The barrier sits at the tool layer because that is the layer that holds on every platform — and, since the measurement above, because the sandbox has been observed not holding on Windows. That narrower claim describes a CLI that accepts the flag and continues, which is Windows and the 2026-08-09 measurement. A current CLI on a kernel without Landlock does not continue: it refuses to start, which is why the bridge passes `off` there instead of asking.

The barrier is applied on every launch path: foreground, background worker, the automatic retry, and review/critique. Each of those is pinned by a test that asserts the argv this bridge builds.

**A thread keeps the sandbox profile it was created with.** The CLI saves a session's sandbox profile, and a resume that asks for a different one exits 1 with `cannot resume this session under sandbox profile '<requested>' — it was created with '<saved>'`; a resume without `--sandbox` takes the saved profile instead (cli-1.0.45 `crates/codegen/xai-grok-pager-bin/src/main.rs:2152-2162`, `crates/codegen/xai-grok-pager/src/app/cli.rs:1008-1022`). `--thread` and `--resume-last` resume a session the bridge itself started, so a thread continued under another profile than the one it began with fails on resume, for instance a read-only thread on a Linux host whose Landlock answer has changed since (`off` one time, `read-only` the next). A read-only thread continued with `--write`, which passes no `--sandbox`, resumes under the saved read-only profile, so on a kernel that enforces it the write run cannot write. The bridge does not work around either: changing a session's confinement halfway through is the CLI's decision to refuse. Start the thread over with `--fresh` when the mode changes. This is read from the 1.0.45 source and has not been measured on a current CLI.

⚠ **What that does NOT cover:** a read-only or connector run cannot start a subagent or a workflow through a tool call. The bare `--deny Edit` and `--deny Write` are both parsed as a tool-wide Edit rule (`rules.rs:248`), that rule reaches the task and workflow tools (`permission_access.rs:35-38`, `policy.rs:547-552`), and it is enforced before any approval mode (`manager/mod.rs:762-776`). Those paths are cli-1.0.45; the same shape is in 1.0.41. Measured 2026-10-15 on grok 1.0.52 with this bridge's read-only flags: the spawn was refused with "Denied by permission policy: deny rule on edit" and no subagents directory appeared. Through a tool call, children exist only in `--write` runs today. This protection is a side effect of how the CLI classifies those tools, not a documented contract, so a CLI change could reopen it. Where a child does run, it shares the parent's permission rules, saved grants and approval mode and carries over the tool removal list — read from the `grok 1.0.41` source (`subagent_spawn.rs`, `acp_session_impl/spawn.rs`), not measured. The tests on our argv assert the flags this bridge passes, which is a different statement from inheritance. Outside tool calls, a prompt whose first text is `/` may be taken by the CLI as one of its own slash commands rather than as a task, so the bridge never sends a read-only `run` prompt whose first character other than Unicode whitespace is `/`: such a prompt goes out behind a one-line note, and the run's warnings say so. Connector prompts already open with the bridge's note, and review and critique prompts are templates. `--write` prompts are sent as given, because write mode confines nothing in the first place. Treat the `explore` path as the conservative case for the toolset (see the note above) rather than assuming a narrower one.

## Connector mode

`run --connector <name>[,<name>…]` lets the agent use the connectors you have signed in to on the Grok side — Google Calendar, Notion, GitHub and so on, the managed MCP gateway xAI runs. **The credential never reaches this plugin or Claude Code.** The Grok CLI holds it and calls the connector itself; the bridge only decides which connectors a run may use. That is the point of the mode: you get a calendar or a Notion page into a task without giving the calling agent the login.

**What it opens, exactly.** Connector mode is the read-only barrier with one opening. Two tools come back — `search_tool` and `use_tool`, the MCP meta-tools — and the `MCPTool` deny rule is dropped. Everything else stays: the shell, the file editor, `write`, the media generators, `web_fetch` and the scheduler are still removed, `Bash`/`Write`/`Edit` are still denied, and `--sandbox read-only` is still passed, except on a Linux kernel whose probe says Landlock is absent, where this mode passes `--sandbox off` for the same reason as every other read-only launch. `--no-plan` is still passed and is not part of the barrier: a headless run does not read it. It cannot be combined with `--write`, `--background` or `--prompts-file`.

**The named connectors are the gate.** Each name becomes one allow rule — `--allow MCPTool(<name>__*)` for a whole connector, `--allow MCPTool(<name>__<tool>)` for an exact tool given as `<connector>__<tool>` — and the run is pinned to `--permission-mode default`. In that mode a headless run answers every permission request it has no rule for with *cancelled*, so a tool no rule covers is refused. **Measured 2026-09-23 against `grok 1.0.41`:** with an allow rule covering only `google_calendar__search`, a call to `google_calendar__list_calendars` came back `User cancelled the execution for tool use_tool` and returned no data. That measured a tool of the same connector outside the rule; a call to a different connector takes the same path in the source but was not called, because the test deliberately touched nothing but the calendar. There is deliberately no "all connectors" value: naming each one is what keeps a calendar task from also being able to send mail. The bridge also opens every connector prompt with a short note naming the connectors the run may use, which is an instruction to the model, not a gate.

⚠ **The gate adds to your own permission settings; it does not replace them.** Everything below is read from the `grok 1.0.41` source; none of it could be switched off by this bridge for a single run, and none of it was present on the machine where the measurement above was made — so if yours carries any of it, the gate is only as narrow as your settings are.

- **Allow rules from your other settings.** The CLI also applies the permission rules from your Grok config (`~/.grok/config.toml`), from managed policy, and from Claude Code's settings: `~/.claude/settings.json` and `settings.local.json` always, and a project's `.claude` and `.grok` settings when that folder is trusted. A deny rule wins wherever it comes from, but an allow rule from any of those adds to the connectors you named: an `mcp__github` allow in your Claude Code settings pre-approves Grok's `github` connector in every connector run. The import itself shows in a live run's debug log.
- **"Always allow" answers you gave in the Grok TUI.** Choosing always-allow for an MCP tool or server there is saved for that repository, and the CLI checks those saved grants before it would ask — so for a run whose `--cwd` is in that repository, they open those connectors too. Read-only was immune, because its `MCPTool` deny is checked first; connector mode drops that deny. A grant made in a TUI session open at the same time takes effect mid-run.
- **Claude Code's `defaultMode`.** `bypassPermissions` there approves everything, and `auto` hands a call nothing else decided to an LLM classifier instead of refusing it. `--permission-mode default` does not override either; it overrides only the Grok setting described next. Whether the classifier would approve a given connector call has not been measured.
- **A local MCP server with a connector's name.** The allow rule matches by name, so `--connector github` also opens a local MCP server called `github` configured for the CLI, and on a name clash `use_tool` calls the local server first, with its own credentials rather than your Grok-side login.

⚠ **Why the mode is pinned:** without `--permission-mode`, the CLI takes the approval mode from `[ui] permission_mode` in `~/.grok/config.toml`, and the TUI writes that setting when you toggle always-approve there. With that setting at `always-approve`, the headless run switched itself to auto-approve before its first turn, and a call outside the allow rule **went through and returned calendar data**. A command-line `--permission-mode` overrides that setting completely — that setting only, not Claude Code's `defaultMode` above — which is why connector mode always passes one. **Read-only `run`, `review` and `critique` do not pin a mode today** and therefore inherit that setting; their barrier is tool removal and deny rules, not the approval mode, but whether every deny rule holds under an inherited always-approve has not been measured.

**A named connector is fully open.** `MCPTool(google_calendar__*)` pre-approves every tool of that connector, including the ones that create, change, send or delete. To keep a read task read-only by mechanism, name its tools instead — `--connector google_calendar__search,google_calendar__get_event` — and a write tool of that connector is refused like any other unnamed tool, with the same additive caveat as above. The mode never retries a run automatically, for the same reason `--write` does not: a retry after a partial run could repeat an action that already happened. Name only what a task needs, say in the prompt what the agent may and may not do with it, and read the result.

**A catalog that never loads is reported, not passed off.** Once in four connector runs on 2026-09-23 the catalog did not load at all, and the run still ended with an ordinary-looking reply. The bridge now reads the run's session history after a connector run that exited 0: when searches came back empty or calls found no such tool, and nothing showed the catalog loaded, the run fails with `connector-unavailable` — nothing reached the connector, so running it again is safe. The check only recognises those two shapes as a missing catalog. A refused call counts neither way, and anything else, including a history it cannot find, leaves the run as it was and says so in a warning. The CLI rewrites `chat_history.jsonl` when a session is spawned and again when retained pruning replaces old tool results, so a byte offset taken before the run does not stay on the turn boundary. Each connector run therefore puts its own marker, `grok-cc-run-` plus random hex, into the note at the head of the prompt, and the check grades only the lines after the last user-message line that contains that marker. The file is read from the tail, at most 8 MiB; a marker that is not in that tail is inconclusive. `connectorCheck.reason` names why a check stopped short: `marker-missing`, `no-sign` (connector calls and neither a positive nor a negative sign), `subagents`, or `unreadable`, and the warning says that reason. A child counts by `started_at` in its `meta.json`. The CLI's orphan heal rewrites `meta.json` and leaves `started_at` alone, which is why a directory timestamp is not the window. When the parent made no connector call and a child started during this run, the warning says the parent made none and the children's calls are not checked. On grok 1.0.52 a read-only or connector run cannot spawn a child through a tool call (measured 2026-10-15: the bare Edit deny rule refuses the task tool with "Denied by permission policy: deny rule on edit"), so that branch is defensive. A catalog missing from the parent while a child started in the run is inconclusive, because the child's calls are in a history of their own.

**A refusal ends the run.** When the allow rules refuse a call, a headless run does not carry on without it: the CLI stops at that moment with `stopReason: cancelled`, and whatever the agent planned after the call does not happen — observed three times out of three. The text left over is whatever the model said before the call. The bridge reports such a run as `connector-refused` whenever the session history shows the refused call, and that takes precedence over a missing catalog: an empty first search followed by a refusal is a refusal, because a re-run is refused the same way whatever the catalog did. So either name the tool in `--connector` or leave the call out of the request. A policy denial (`Tool use_tool was not executed: …`) and an unresolved MCP permission (`MCP permission was not resolved to Allow`) do not end the turn: the CLI continues, and the bridge counts those calls and warns that they were refused and the run continued, without failing the run as `connector-refused`. A classifier block that lets the run continue is recorded in that policy-denial shape and is counted the same way. Sibling results ("Tool execution cancelled due to earlier …") and the synthetic dangling-call texts are not refusals and are not evidence that the catalog loaded. When the run ended `cancelled` and the history was read and shows no refusal, the leftover text is returned with a warning that the history does not show one. When the history was not read — a non-zero exit, which is also how `--max-turns` exhaustion reports `cancelled` — the warning says the run ended cancelled and its history was not checked, and it does not suggest a refusal. Those two warnings are not both emitted for one run.

**The catalog arrives late.** A headless process fetches the connector catalog in the background after it starts; measured between half a second and about twelve seconds, once after a retry. Until it lands, `search_tool` reports `status: ready` with no tools, and a model that searches once concludes there are none. The bridge cannot wait for the catalog itself — the CLI exposes no way to — so its note at the head of every connector prompt tells the agent to repeat `search_tool` until it returns tool names. That is an instruction, not a guarantee: a run can still end with a confident "no such tool", and since connector runs are never retried, read the answer.

**Residuals.** A tool call cannot start a subagent or a workflow in a read-only or connector run. The bare `--deny Edit` and `--deny Write` reach those tools and are enforced before any approval mode (cli-1.0.45 `permission_access.rs:35-38`, `policy.rs:547-552`, `manager/mod.rs:762-776`). Measured 2026-10-15 on grok 1.0.52 with this bridge's read-only flags: the spawn was refused with "Denied by permission policy: deny rule on edit" and no subagents directory appeared. Children exist only in `--write` runs today. This protection is a side effect of how the CLI classifies those tools, not a documented contract, so a CLI change could reopen it. Where a child does run, it shares the parent's permission rules, saved grants and approval mode and carries over the tool removal list — that is read from the `grok 1.0.41` source (`subagent_spawn.rs`, `acp_session_impl/spawn.rs`), not measured. Outside tool calls, the CLI's slash dispatcher acts on a prompt whose first text begins with `/`; a connector prompt never does, because the bridge's note comes first. What a connector returns is untrusted input on the same terms as fetched web content above, and it enters the model's context the same way — so an event description or a page can ask the model to call another connector, and the settings listed above decide whether that call is refused. **And a named connector is an outbound door as well as an inbound one**: whatever the agent can read — any file the user account can read, including `~/.ssh`, `~/.claude` and `~/.grok`, not only the files under `--cwd`, plus what another connector returned — it can also write into a connector that accepts text, a Notion page or an event description. `--cwd` sets the working directory and the base for relative paths. It does not bound reads. Pointing it at an empty directory does not keep those files out of the model's context or out of a writable connector. That is the CLI's design in 1.0.41 and 1.0.45; 1.0.52 is unverified from source. The bridge's result does not list which tools the agent called; the only record is the Grok session history, under the session id in the `--json` payload. An audit of it has to follow one more hop: a large tool result is cut to about 20 KB in `chat_history.jsonl` and ends in a pointer to the full output in the session's `mcp\` folder, so the cut text itself does not parse.
